# OP2P White Label

## Project Overview

## Цель проекта

Проект представляет собой white-label веб-платформу для работы с системой Only P2P.

Пользователь взаимодействует исключительно с нашим сайтом.

Все операции с балансом, пополнением, реквизитами, заявками и поддержкой выполняются системой Only P2P через официальное REST API.

Наш проект выступает в роли безопасной прослойки между пользователем и системой Only P2P.

---

## Основные задачи проекта

Проект должен предоставлять пользователю полноценный личный кабинет, в котором доступны:

- регистрация и авторизация;
- управление профилем;
- просмотр баланса;
- пополнение баланса;
- управление банковскими реквизитами;
- просмотр и обработка заявок;
- загрузка подтверждений оплаты;
- общение с поддержкой.

---

## Архитектурная концепция

Проект разделён на два независимых сервиса.

Frontend

Frontend отвечает за пользовательский интерфейс, взаимодействие пользователя с системой, отображение данных, управление состоянием интерфейса и отправку запросов в Backend.

Backend

Отвечает за безопасность, авторизацию, хранение внутренних данных и взаимодействие с Only P2P API.

Frontend никогда не взаимодействует напрямую с Only P2P.

Все запросы проходят исключительно через Backend.

---

## Источник бизнес-логики

Основная бизнес-логика находится на стороне Only P2P.

Наш Backend не реализует:

- расчёт балансов;
- обработку заявок;
- обработку платежей;
- работу поддержки;
- криптовалютные операции.

Backend является центральной частью системы.

Он отвечает за безопасность, авторизацию пользователей, хранение внутренних данных, взаимодействие с Only P2P API, валидацию запросов, обработку ошибок и защиту внутренних сервисов.

Передача запросов к Only P2P является лишь одной из его обязанностей.

## Основные принципы проекта

При разработке необходимо придерживаться следующих принципов.

### Security First

Безопасность важнее скорости разработки.

Любое решение должно рассматриваться с точки зрения безопасности.

При возникновении конфликта между удобством разработки и безопасностью всегда выбирается безопасное решение.

Любое изменение архитектуры должно оцениваться с точки зрения безопасности.

---

### Production Ready

Все решения должны соответствовать production-уровню.

Не допускаются временные упрощения архитектуры.

---

### Clean Architecture

Каждый модуль должен иметь одну ответственность.

Минимальная связанность между компонентами.

---

### Strict Type Safety

Весь проект разрабатывается на TypeScript.

Использование any допускается только в исключительных случаях с обязательным документированием причины.

Во всех остальных случаях должна использоваться строгая типизация.

---

### AI Friendly

Архитектура проекта должна быть максимально понятной как человеку, так и AI-ассистентам.

Все крупные решения документируются.

## Внешние зависимости

Only P2P REST API

Backend является единственной точкой взаимодействия с внешним API.

Frontend никогда не получает:

- api_id
- secret_key
- внутренние служебные параметры

---

## Статус документа

Документ является базовым описанием проекта.

При изменении архитектурной концепции обновляется в первую очередь.

## Что не входит в проект

Проект не реализует собственную P2P платформу.

Не выполняет:

- хранение криптовалюты;
- обработку платежей;
- проведение финансовых операций;
- расчет балансов;
- обработку споров;
- работу операторов поддержки.

Весь перечисленный функционал предоставляется системой Only P2P.

## Архитектурные ограничения

В рамках проекта действуют следующие ограничения.

- Frontend никогда не обращается напрямую к Only P2P API.
- Backend никогда не раскрывает секретные ключи.
- Любая бизнес-операция проходит через Backend.
- Все внешние запросы проходят валидацию.
- Любые изменения API должны быть отражены в документации.

## Источник истины

При возникновении противоречий между:

- документацией проекта;
- комментариями в коде;
- реализацией;
- AI-предложениями;

приоритет имеет следующая последовательность:

1. Актуальная документация проекта.
2. Требования заказчика.
3. Документация Only P2P API.
4. Реализация кода.

Если код противоречит документации — код должен быть приведен в соответствие документации либо документация должна быть официально обновлена.

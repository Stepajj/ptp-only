# Architecture Decision Log (ADR)

## Purpose

This document records important architectural and engineering decisions made during the project.

Its purpose is to preserve the reasoning behind technical choices.

Understanding *why* a decision was made is often more valuable than knowing *what* was implemented.

---

# How To Use

Every significant technical decision should be recorded here.

Examples include:

- architectural changes;
- technology replacements;
- security decisions;
- database redesign;
- API redesign;
- major refactoring;
- performance-related decisions.

Minor implementation details should not be recorded.

---

# Rules

Every architectural decision should be:

- understandable;
- traceable;
- documented;
- dated.

Old decisions should never be deleted.

If a decision changes, mark it as:

- Deprecated

or

- Replaced

and create a new ADR.

---

# Relationship With Documentation

If an ADR changes the architecture, the following documents should also be reviewed:

- Project Overview
- Architecture
- Security
- Domain Model
- API Integration
- Database
- Backend
- Frontend

Documentation should always remain synchronized.

---

# Future Evolution

As the project grows, this log will become the historical record of engineering decisions.

The goal is not to record every implementation detail, but to preserve the reasoning behind important technical choices.
